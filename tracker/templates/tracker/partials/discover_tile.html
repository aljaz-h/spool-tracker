Revealed via an animated `clip-path` (inset(100% 0 0 0) -> inset(0 0 0 0) on an always-fully-laid-out, absolutely-positioned panel), not a `transform` (translate-y) and no longer a `grid-template-rows` trick either (an earlier version of this used grid-rows - clip-path replaced it because animating grid-template-rows is a layout property, so the browser re-runs layout every frame, which read as choppy/disjointed next to the poster's own GPU-composited hover-zoom below; clip-path is paint-only, no layout recalculation, and stays perfectly in sync with that zoom at the same duration/easing). Not a transform because a `transform` on an ancestor creates a new containing block for any `position: fixed` descendant, and the watched/list buttons' own popovers (poster_card_watched_button.html etc.) are fixed-positioned via window.positionPopover's own viewport-relative math (base.html) - nesting them inside a transformed overlay would silently break that positioning the moment the overlay's transform left its resting value. clip-path does not establish a containing block for fixed descendants (only transform/perspective/filter/backdrop-filter/will-change/contain do), so it doesn't have that problem, and - being absolutely positioned the whole time regardless of technique - the panel was never using grid-rows/clip-path for its layout space to begin with, only as a clip animator. The poster art itself (the , or the gradient placeholder div when there's no poster_url - both plain siblings of the reveal panel below, not its ancestors, so scaling them can't touch the popovers' containing-block either) gets its own small `scale` zoom on the same hover, purely cosmetic ("pop out a bit"). None of this - the reveal, the zoom, or the "dim" mode's opacity below - triggers off CSS `:hover`/`:focus-within` at all, deliberately. It's driven by `.tile-hover`/`.tile-focus`, plain classes base.html toggles itself via delegated mouseover/mouseout/focusin/focusout listeners on `.discover-tile` (this template's own marker class on the outer wrapper). That's not a style preference - it's the fix for a bfcache bug that went through several failed CSS-only and hybrid attempts first (see base.html's own comment on that listener for the full history): browsers don't re-run :hover hit-testing on a bfcache restore, so a tile clicked into and then backed out of stays visually "hovered" with the pointer nowhere near it - and, confirmed live across multiple different fixes tried, the browser's own internal :hover cache never reliably self- corrected afterward no matter what real interaction happened next, or where. Owning the trigger as a plain class instead sidesteps that category of bug entirely: on restore, base.html unconditionally clears every `.tile-hover`/`.tile-focus` it finds - a plain classList.remove is definitive, not a guess about an opaque browser cache - and real subsequent hover/focus re-adds them exactly as on any fresh load, no special-casing needed.
