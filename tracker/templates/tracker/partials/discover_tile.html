Split into two independently-revealed pieces - discover-tile-reveal-text (title/year/genres) and discover-tile-reveal-actions (the watched/list buttons) - that look like one unit but deliberately aren't, because they can't share an ancestor that clips: the buttons' own popovers (poster_card_watched_button.html etc.) are fixed-positioned via window.positionPopover's own viewport-relative math (base.html), and confirmed live (an actual screenshot, not just the popover's computed position - the position was always correct, the clipping wasn't visible in coordinates) - clip-path clips a position:fixed descendant's *paint* to its own box exactly like overflow:hidden does, at every inset value including a fully "open" inset(0 0 0 0), not just while animating - so a popover opened from inside a clipped ancestor rendered, but only the sliver of it inside that small bottom panel's own box was ever visible, the rest cut clean off. (A `transform` has the same problem one level up - it creates a new containing block for fixed descendants in the first place, so this was never an option either.) The fix isn't a smarter clip - there isn't one; nothing clips only "the part of me that isn't a fixed popover" - it's not clipping the buttons' subtree at all: discover-tile-reveal-actions lives *outside* the overflow-hidden/rounded poster box (a sibling of it, not a descendant), positioned by its own known height instead, and reveals via opacity, a property that changes compositing alpha but never clips a descendant's paint regardless of where that descendant renders. discover-tile-reveal- text has no such constraint (a plain text link, nothing fixed-positioned inside it), so it keeps the clip-path slide-up animation exactly as before, sitting directly above the button row. The poster art itself (the , or the gradient placeholder div when there's no poster_url - both plain siblings of the reveal panel below, not its ancestors, so scaling them can't touch the popovers' containing-block either) gets its own small `scale` zoom on the same hover, purely cosmetic ("pop out a bit"). None of this - the reveal, the zoom, or the "dim" mode's opacity below - triggers off CSS `:hover`/`:focus-within` at all, deliberately. It's driven by `.tile-hover`/`.tile-focus`, plain classes base.html toggles itself via delegated mouseover/mouseout/focusin/focusout listeners on `.discover-tile` (this template's own marker class on the outer wrapper). That's not a style preference - it's the fix for a bfcache bug that went through several failed CSS-only and hybrid attempts first (see base.html's own comment on that listener for the full history): browsers don't re-run :hover hit-testing on a bfcache restore, so a tile clicked into and then backed out of stays visually "hovered" with the pointer nowhere near it - and, confirmed live across multiple different fixes tried, the browser's own internal :hover cache never reliably self- corrected afterward no matter what real interaction happened next, or where. Owning the trigger as a plain class instead sidesteps that category of bug entirely: on restore, base.html unconditionally clears every `.tile-hover`/`.tile-focus` it finds - a plain classList.remove is definitive, not a guess about an opaque browser cache - and real subsequent hover/focus re-adds them exactly as on any fresh load, no special-casing needed.
