{% comment %} context: label (optional - omit/blank when the caller already shows this dimension's name elsewhere, e.g. a collapsible row's own , so it isn't printed twice), name_from, name_to, min, max, step (optional, default 1), from_var, to_var (Alpine data property names in the enclosing x-data), suffix (optional, e.g. " min") - the enclosing element must already have from_var/to_var declared in its x-data. Position math accounts for the 16px thumb (see .dual-range-thumb in app.css) - a plain 0-100% mapping would place the fill bar/labels at the container's true edges, while the native thumb's own center never quite reaches them (browsers keep a range input's thumb fully inside its track, so at value=max the thumb's center sits at 100% - half its width, not literally 100%). calc(fraction * (100% - 16px) + 8px) matches that native positioning instead of drifting from it. x-cloak keeps the fill bar/labels hidden until Alpine has applied that calculation at least once, instead of briefly showing the pre-hydration unstyled (effectively full-width) state. Each thumb's own min/max is bound to the *other* thumb's live value (:max on the from-input, :min on the to-input) so the browser's native range-dragging behavior itself refuses to cross them, rather than reacting after the fact - a first attempt tried clamping the bound value from an @input handler instead, but Chrome (and others) keep rendering a range thumb at the raw pointer position while the mouse button is still down regardless of the element's own .value being reset from JS mid-drag, so the thumb visibly sailed straight through the other one even though the submitted value was technically clamped. Constraining min/max is a real HTML5 input-level constraint the browser enforces live during the drag itself, not just on release. {% endcomment %}
